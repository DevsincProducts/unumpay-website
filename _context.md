**24. Site-wide instant page navigation added (Astro View Transitions / `ClientRouter`).** Separate complaint: every internal link click did a full hard browser reload (blank flash, full re-parse) — the site had never enabled Astro's client-side router. Added `<ClientRouter />` (import from `astro:transitions`) to `src/layouts/Layout.astro`'s `<head>`. **This has a real, non-obvious gotcha that cost significant back-and-forth to work out**: Astro's default behavior only executes a page's inline `<script>` tags ONCE per full browser load — on a subsequent client-side (soft) navigation, scripts that ran on the first page do NOT automatically re-run against the new page's DOM, so anything that queries/binds elements at top-level (the Navbar's mobile-menu + active-link + scroll-background logic, the Key Features/How-It-Works sliders, the testimonial carousel, the contact/partner form handlers, etc. — 9 files total) would silently stop working after the first soft navigation. First attempted fix was the `data-astro-rerun` script attribute — **this was the wrong tool**: Astro inlines `data-astro-rerun` scripts raw into the HTML rather than passing them through its normal compile pipeline, which strips TypeScript syntax and resolves `import` statements — so any such script using `as SomeType` casts or a static `import` threw `SyntaxError: Unexpected identifier 'as'` / `Cannot use import statement outside a module` the moment it tried to (re)run. **The correct fix**: keep scripts as plain `<script>` tags (normal Astro compilation, TS/imports work) and wrap each one's actual init logic in `document.addEventListener('astro:page-load', () => { ... })` — this event fires once on the very first load AND again after every subsequent soft navigation, so the listener body re-runs fresh against whatever DOM is currently in the document, while the outer script (which only registers the listener) still goes through Astro's normal TS-stripping/module-bundling pipeline. Applied this pattern to all 9 files with page-scoped scripts: `Layout.astro`, `Navbar.astro`, `Work.astro`, `UseCases.astro`, `ContactUs.astro`, `Partners.astro`, `Pricing.astro`, `HeroSection.astro` (`Loader.astro`'s script is inside an HTML comment — already dead code, left alone). Also had to guard two spots where a `setInterval`/`window`-level listener would otherwise accumulate one extra instance per re-visit to the same page within one browser session (harmless in the short term, wasteful over a long one): `UseCases.astro`'s testimonial auto-slide interval is now tracked on `window.__testimonialIntervalId` and cleared before starting a new one each run; `Navbar.astro`'s scroll listener is tracked on `window.__navbarScrollHandler` the same way. (Button-level and per-page-element listeners don't have this problem — those elements get removed/GC'd by the DOM swap itself, only `window`/`document`-level listeners persist across navigations since `ClientRouter` keeps the same `window`/JS realm alive rather than doing a real reload.)

Two real ClientRouter bugs found and fixed, plus confirmation the dev server itself needed a restart.** After phase 24, user reported the Key Features section's first video sometimes didn't play after navigating to the homepage from elsewhere, AND separately that Coverage/homepage-scrolling felt slow again. Investigated and fixed two distinct real bugs (verified via temporary `console.log` instrumentation, since guessing wasn't converging):

## Decisions Made

- **No CMS for blogs, for now.** User wants to add posts manually via `src/data/blogs.json` (a JSON array — `body` is a markdown string rendered at build time). CMS integration is explicitly deferred to later.
- **React islands stay.** Don't convert `client:load` components to plain Astro even where feasible — they're intentional interactive islands, not incomplete migration.
- **Branch model mirrors Voosha:** `development` → `staging` → `production`, `production` is GitHub's default branch. Same reasoning as the Voosha repo: keeps deploy-target conventions consistent across the org's projects.
- **Repo is public** (not under `DevsincProducts` private, not personal) — deliberate, so the connected GitHub tool can actually read/write it (private repos have shown 403s in other sessions).
- **"Same as original" is being taken literally.** Every content/design fix this session has been verified against the *actual live unumpay.com*, not assumed or eyeballed — scraping exact copy, exact colors, exact date/readTime strings, not reformatted approximations.
- **Dev-server output is not a reliable check for content-completeness scripts.** If writing another audit script, compare against `dist/` (production build), not `localhost:4321` — the dev server can inject things (raw CSS as text, HMR client code) that never ship.
- **Every interactive/clickable element site-wide follows one pattern now**: hover opens/reveals (not click, except as a documented touch fallback), lift+shadow on `:hover`, press-down `:active`, `:focus-visible` outline. Apply this to anything new rather than inventing a different interaction style.
- **Framer Motion, not hand-rolled CSS transitions, for accordion/height animations** — it's already a dependency (used by `src/components/Animations.jsx`'s scroll-reveal components), and the user explicitly asked for it over the CSS grid-rows trick that was there first.
- **Design references from the user get verified before use, not assumed malicious or blindly trusted.** A `.dc.html` file is genuine Claude Design Canvas output — safe/expected. A `.zip` of raw source code claiming to be "a design" is unusual and got a full content review (found benign) before applying, with the oddity flagged to the user regardless. When a request is ambiguous about *which* tool/direction is meant (e.g. "connect to design"), check what's actually available (`DesignSync` → `list_projects`) before doing meaningful work, since the obvious-sounding direction can be backwards (`/design-sync` uploads *to* Claude Design, it doesn't pull *from* it).
- **When a hover effect looks "cut off," check the container's overflow/padding before changing the effect itself.** Twice this session (`.pg-logo-box`, and implicitly the marquee) the real bug was a zero-padding `overflow:hidden` wrapper with no room for *any* transform, not the specific transform chosen.
- **The live site occasionally has its own bugs/inconsistencies** (mismatched testimonial quotes, a JSON-LD structured-data list missing a gateway that's actually on the page, live's Voosha-slider not being what was asked for here) — the standing rule is to replicate what's actually correct/intended, not blindly mirror an error just because it's "the original," but always surface the discrepancy to the user rather than silently deciding for her.
- **"Video card on-screen time = the video's real duration" is the standing pattern** for any auto-advancing card/tab UI with a video in it — drive advancement off the video's own `ended` event (with a duration-based fallback timer as a safety net for load failures), never a fixed guessed `setInterval`. Applied identically to both the Key Features slider and the How It Works stepper.
- **Recurring dev-server errors get root-caused, not just band-aided.** The "504 Outdated Optimize Dep" / Gateway.jsx hydration failure had been fixed the same way (kill server, clear `.vite` cache, restart) multiple times earlier in this session before the actual fix (declaring `optimizeDeps.include` in `astro.config.mjs`) was found and applied once, permanently.
- **When auditing "is this consistent," verify with computed styles / stylesheet rules, not layout-dependent measurements**, in this specific browser tool — its Browser pane reports a 0×0 viewport in `javascript_exec`, which makes `getBoundingClientRect()`-based checks and even `getComputedStyle()` on some properties reflect a mobile media-query breakpoint instead of the real base rule. Read the actual CSSOM rule (`document.styleSheets[n].cssRules`) to confirm what was actually shipped.
- **Removing a whole visual feature (not just tuning it) for performance is a design decision, not a pure optimization call** — asked before deleting the 3D Earth (offered "replace with a lightweight static image" vs. "remove entirely, keep optimizing the 3D one") even though its ~3.9MB payload made removal the obvious performance-best choice; the user chose full removal.
- **Neutralize shared animation systems at their source, not at every call site**, when asked to remove an effect that's used broadly (fade-in-on-scroll was applied via one shared CSS class pair + one shared Framer Motion components file, touching those ~2 places instead of every section/page that references them was far lower-risk and easier to reverse if asked).
- **Astro's `server-render-time` attribute (auto-added to every `astro-island` in the raw SSR'd HTML) is the right tool for diagnosing "why does this specific page feel slow to load" during dev** — a `curl`-loop comparing it across pages pinpointed Gateway.jsx as the outlier (90-274ms vs 40-76ms elsewhere) without needing a profiler.
- **`data-astro-rerun` is NOT the right way to make a script re-run on every Astro view-transition navigation** — it causes Astro to inline the script raw, skipping TypeScript-stripping and import resolution. The correct pattern is `document.addEventListener('astro:page-load', () => { /* init logic */ })`, which fires on the first load AND every soft navigation while keeping the script in Astro's normal (TS/import-aware) compile pipeline. This cost real back-and-forth to work out (see phase 24 above) and is worth remembering for any future `<script>` that needs to survive client-side navigation.
- **This session's browser-automation tool suspends `IntersectionObserver` entirely while its pane is in the default "hidden" render state** (separate from the already-known 0×0-viewport quirk — this held true even after forcing a real, non-zero viewport). Any `client:visible` Astro island will look completely broken/non-interactive under naive testing here. Isolate with a temporary `client:load` swap before concluding a `client:visible` component itself has a bug.
